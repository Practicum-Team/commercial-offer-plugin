Активный профиль компании и реестр профилей хранятся в `config.json` в папке profiles проекта. 
Каждый вызов CLI читает актуальный `config.json` и записывает изменения атомарно. 
Агент не работаетс файловой системой напрямую — только через подкоманды `profiles-*`.

## Профиль компании

1. Загрузка: пользователь либо прикрепляет документы в чат и называет профиль,
   либо указывает путь к каталогу. Файлы: catalog, prices, rules, cases, profile,
   template (расширения из белого списка, реальный тип проверяется).
2. Агент вызывает `profiles-check` по каждому файлу. При ошибке — сообщить
   пользователю и запросить корректный файл.
3. Загрузка: `profiles-load <name> <files> [--dir PATH]`.
   - `status=needs_confirmation` → спросить пользователя «заменить/оставить»
     и повторить с `--overwrite yes|no`.
   - `status=ok` → профиль зарегистрирован и сделан активным.
4. Смена профиля: `profiles-use <name>`. Проверить через `profiles-list`.
5. Все пути к документам брать из активного профиля (`Config.document_path`).
   Прямые операции с ФС агентом запрещены — только CLI.


## Импорт профиля в SQLite

1. `profiles-inspect <name> <files>` → получить `llm_prompt` и отпечатки.
2. Вызвать LLM с промптом; сохранить её JSON в `data-schema.json`.
3. **СТОП.** Показать пользователю таблицу `файл → назначение` и `field_map`.
   Ждать явного «да». При «нет» — принять ручные назначения, повторить шаг 2.
   После «да»:
   - `profiles-confirm <name> data-schema.json schema --yes`
   - `profiles-confirm <name> data-schema.json fields --yes`
4. `profiles-apply-schema ...` — при ошибках показать пользователю, пересобрать схему.
5. `profiles-validate ...` — при ошибках показать файл и строку пользователю.
6. `profiles-commit ...` — CLI сам проверит, что все подтверждения записаны и
   соответствуют текущему хэшу схемы. Если `ok=false, stage=confirmation` —
   это значит, что пользователь не подтвердил; вернуться на шаг 3.
   Отдельный вызов `profiles-confirm ... commit --yes` — только после того,
   как пользователь увидел итоговые `counts` (dry-run) и сказал «загружай».

## Запреты

- Нельзя вызывать `profiles-confirm ... --yes` без явного согласия пользователя
  в предыдущем сообщении. Агент не подставляет согласие «по умолчанию».
- Нельзя обходить `profiles-commit`: только через эту команду, напрямую
  в SQLite агент не пишет.
- При `stage=confirmation` или любом `ok=false` — остановиться и вернуть
  пользователю текст из поля `next`/`errors`.


## Поиск и request-schema

### Сбор запроса
1. Спросить: тип клиента, наименование, контактное лицо, телефон, email, запрос, бюджет.
   Либо принять всё одним JSON — см. пример в references/data-formats.md.
2. Если бюджет не указан — спросить: «Есть ли ограничения по бюджету? Если да — уточните, подберу точнее.».
   Отказ фиксировать в `ограничения` как `budget_not_provided`.
3. Валюта: если явно не названа — взять из `profile.json` (поле `currency`).
4. Дата покупки: из текста; иначе — сегодняшняя.

### request-schema.json
Формируется LLM из ответов пользователя. Поля: profile_id, тип клиента, контактные
данные, запрос, бюджет, валюта, дата покупки, скидка, ожидаемые_товары,
допустимые_варианты, обязательные_уточнения, ограничения.
См. `references/data-formats.md`.

### Поиск (только через CLI)
1. `search-products <name> --currency --budget --purchase-date --category`.
   LLM анализирует кандидатов на соответствие запросу.
2. Для отобранных: `search-rules <name> --product-id ... --category ...`.
   Если в запросе явная скидка — `--check-discount`, LLM сверяет со всеми правилами.
3. Успех → итоговый JSON с ожидаемыми_товарами и ограничениями → в чат.

### Fallback
Если кандидатов нет, или они не соответствуют запросу клиента:
1. `search-dump <name> --currency` — полный дамп; LLM ищет соответствия.
2. `search-rules` по найденным (или `--check-discount`).
3. Если снова пусто — `обязательные_уточнения`. Коды неточностей:
   `quantity_unspecified`, `ambiguous_rules`, `conflicting_requirements`,
   `unit_mismatch`, `missing_product`, `insufficient_budget`, `incomplete_request`.
   Формат: `[{"неточность": "код", "вопрос": "..."}]` → отправить пользователю.
4. Получив ответы — обновить request-schema.json и повторить основной поиск.
