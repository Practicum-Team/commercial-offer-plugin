## Этап 0. Подготовка профиля

Шаги:
1. Получить от пользователя: имя профиля и один из вариантов — вложенные файлы
   или явный путь (`--dir`).
2. `profiles-check` для каждого файла. Не прошёл — стоп, уточнить у пользователя.
3. `profiles-load`. Возможные статусы:
   - `needs_confirmation` — задать вопрос по каждому конфликту, затем повторить
     с `--overwrite`.
   - `ok` — профиль активен, перейти к следующему этапу.
4. Смена профиля в середине сессии: `profiles-use <name>`, затем перечитать
   документы через программные инструменты (кеш не использовать).

## Этап 1. Стадии импорта и переходы

- inspect → apply-schema: без отпечатков LLM не может назначить файлы.
- apply-schema → validate: только при `ok=true`. Иначе стоп.
- validate → commit: только при `ok=true`. Иначе стоп и уточнения.
- commit: идемпотентен по (profile_id, <kind>_id) через merge.
  Повторный вызов с той же схемой обновляет записи, не дублирует.


## Этап 2. Поиск продуктов в БД

- Вход — request-schema.json (см. data-formats.md).
- Порядок: search-products → LLM-анализ → search-rules → LLM-сверка скидки.
- Fallback: search-dump → LLM-анализ → search-rules.
- Не найдено после fallback → сформировать `обязательные_уточнения` по коду неточности,
  отправить пользователю, дождаться ответов, пересобрать request-schema.json,
  повторить с шага search-products.
- Ограничения `["2","14","12","13"]` — служебные коды правил/допущений,
  возвращаются как есть; в текст КП не переносятся, кроме явно согласованных
  пользователем.
