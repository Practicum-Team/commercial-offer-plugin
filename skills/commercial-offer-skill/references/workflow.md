## Этап 0. Подготовка профиля

Шаги:
1. Получить от пользователя: имя профиля и один из вариантов — вложенные файлы
   или явный путь (`--dir`).
2. `profiles-check` для каждого файла. Не прошёл — стоп, уточнить у пользователя.
3. `profiles-load`. Возможные статусы:
   - `needs_confirmation` — задать вопрос по каждому конфликту, затем повторить
     с `--overwrite`.
   - `ok` — профиль активен, перейти к следующему этапу.
4. Смена профиля в середине сессии: `profiles-use <name>`, затем перечитать
   документы через программные инструменты (кеш не использовать).

## Этап 1. Стадии импорта и переходы

- inspect → apply-schema: без отпечатков LLM не может назначить файлы.
- apply-schema → validate: только при `ok=true`. Иначе стоп.
- validate → commit: только при `ok=true`. Иначе стоп и уточнения.
- commit: идемпотентен по (profile_id, <kind>_id) через merge.
  Повторный вызов с той же схемой обновляет записи, не дублирует.


## Этап 2. Поиск продуктов в БД

- Вход — request-schema.json (см. data-formats.md).
- Порядок: search-products → LLM-анализ → search-rules → LLM-сверка скидки.
- Fallback: search-dump → LLM-анализ → search-rules.
- Не найдено после fallback → сформировать `обязательные_уточнения` по коду неточности,
  отправить пользователю, дождаться ответов, пересобрать request-schema.json,
  повторить с шага search-products.
- Ограничения `["2","14","12","13"]` — служебные коды правил/допущений,
  возвращаются как есть; в текст КП не переносятся, кроме явно согласованных
  пользователем.


## Этап 3. Этап расчёта и генерации DOCX

### Предусловия

- `profiles-commit.ok == true` для активного профиля;
- `search-results.json.обязательные_уточнения == []`;
- `search-results.json.ожидаемые_товары` непусто;
- в `request-schema.json`: `profile_id` = активный профиль; `бюджет` задан или
  `budget_not_provided` в `ограничения`; `валюта` задана или `null`.

Если любое условие не выполнено — стоп, вернуться на соответствующий этап.

### Последовательность вызовов

1. `template-fields` → `{ "ok": true, "fields": [...] }`.
   Сохранить полный список. Разбить на:
   - **вычисляемые** (заполняет pipeline из `quote`):
     `ID_<n>`, `позиция_<n>`, `кол_<n>`, `ед_<n>`, `цена_<n>`, `сумма_<n>`,
     `кол_р_<n>`, `услуга_<n>`, `оборудование_<n>`, `кол_об_<n>`, `ед_об_<n>`,
     `итого_работы`, `итого_оборудование`;
   - **текстовые/справочные** — заполняются через `confirmed.json`.
   Если `template-fields` вернул `ok=false` — нет `template.docx`: запросить
   файл у пользователя, не продолжать.

2. Сформировать `confirmed.json` для текстовых/справочных полей.
   Источники — строго из `request-schema.json`, `search-results.json`,
   `profile.json`, `quote` (после расчёта; но до вызова — по данным запроса).
   Правила:
   - `ФИО_представителя_заказчика`, `телефон`, `email`,
     `наименование/ФИО_заказчика` ← `request-schema.json`;
   - `описание_задачи_клиента` ← `request.запрос` (дословно);
   - `обоснование_выбора_решения`, `почему_решение`, `соответствие_требованиям`,
     `текущее_состояние`, `объект_инфраструктура` ← сформулировать по данным
     `search-results.json` и правилам; без вымышленных фактов;
   - `срок_действия_расчёта`, `предоплата`, `номер_КП`, `ФИО_подписанта`
     ← `profile.json`; при отсутствии — «—»;
   - `ограничения_по_срокам_бюджету_условиям` ← бюджет/валюта из
     `request-schema.json` + ограничения из `search-results.json`.
   Вычисляемые поля в `confirmed.json` не включать.

3. `proposal-prepare <search_results> <request_schema> --output <path>
   --confirmed confirmed.json`.

4. Разбор ответа:
   - `stage=input` → показать `error`; попросить пользователя проверить JSON.
   - `stage=proposal` + `error` начинается с «Не заполнены поля шаблона:» →
     а) если перечислены только текстовые поля — дополнить `confirmed.json`
        и повторить шаг 3 (один раз);
     б) если есть вычисляемые поля — сообщить пользователю как дефект
        pipeline; не ретраить.
   - `stage=proposal` + `error` «обязательные уточнения» → вернуться к этапу
     уточнений;
   - `stage=proposal` + `error` «пустой ожидаемые_товары» → вернуться к поиску;
   - `stage=proposal` + `error` «нет template.docx» → запросить файл;
   - `stage=proposal` + `error` про дату («используйте текущую дату») →
     пересобрать `request-schema.json` с `дата покупки = null` (сегодня);
   - `ok=true` → передать пользователю `document_path`, `quote.grand_total`,
     `quote.currency`, `quote.discount_total`, `confirmed_used`.

### Правило одного повтора

Повторный `proposal-prepare` разрешён **только** если был изменён
`confirmed.json` (добавлены/исправлены текстовые поля) или
`request-schema.json` (дата покупки). В остальных случаях — стоп и отчёт
пользователю.

### Запреты

- Не вызывать `prepare_company_proposal`/`proposal-prepare` в обход CLI.
- Не изменять `template.docx` и не редактировать готовый DOCX.
- Не подставлять в `confirmed.json` вычисляемые поля.

### Аудит

Каждый `proposal-prepare` пишет строку в `profiles/<name>/audit.jsonl`:
`{"event":"proposal-prepare","schema_hash":...,"ok":...,"document_path":...}`.
При разборе инцидента сверять: был ли `profiles-commit` до этого, совпадает
ли `profile_id`, нет ли ретраев без изменения `confirmed.json`.

## Жизненный цикл run

1. `runs-start` → `runs.insert`.
2. `runs-finish` → `runs.update(result_kind, document_path)` 
3. При `needs_clarification` — `runs-finish` тоже вызывается; следующий круг
   начинается с нового `runs-start`.
